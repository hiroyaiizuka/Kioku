# Kioku 製品計画

## 目的と確定事項

PC の Obsidian 内で、学習メモから候補を人が選び、採用カードを元メモ内に保存し、タグのデッキで間隔反復する。候補選択とデッキ選択は中央ポップアップ。回答を先に隠してアクティブリコールする。要件案は検討中であり、提案を確定要件と取り違えない。

## M0 受入条件（LEV-274）

- ID `kioku`、名称 Kioku、desktop only。左 ribbon「フラッシュカード」とコマンドで中央の起動確認 modal を開く。
- 画面と README にカード機能未実装を明示する。ノートを読まず、書かず、fake deck を出さない。
- `npm ci` と `npm run check`。metadata、公式 lint、strict 型、意味のある test、production build、配布ハッシュ、CI、任意で非スキップの hook。
- 新規専用 Vault だけを prepare。update は既存 Markdown/config を変えず built plugin files だけを更新。preflight は containment、hash、ID/version/build、enablement を検査。
- docs、AGENTS、独立レビュー、再実行可能な native smoke。実機は enable → ribbon → modal → close → desktop restart 後の再確認。証跡なしに PASS と言わない。

## M1 受入条件（LEV-275）

- 開いているメモ・選択テキストから明示的 Q/A を抽出し、中央ポップアップで原文確認・編集・採用・破棄する。採用時だけ元メモへ保存する。
- 保存形式・安定 ID・再抽出の重複判定を先に設計する（`docs/architecture.md` の「M1 明示 Q/A」）。
- Excalidraw Data・コードブロックを除外し原文を保持する。開いたノートは Editor、閉じたノートは `Vault.process` で原文照合する。
- 日本語、同名見出し、Undo/Redo、外部変更、複数ビューを専用 Vault の実機で検証する。デッキ・復習・AI は作らない。

## M1 で決めたこと（LEV-275 の設計判断）

詳細と理由は `docs/architecture.md` の「M1 明示 Q/A」。

- **明示 Q/A 構文**：行頭の `Q:`/`問:`（全角コロン・全角 Ｑ 可）から始まり `A:`/`答:` を含むブロック。空行・見出し・次の問いで終わる。
- **保存構文と安定 ID**：元ブロック最終行末へ Obsidian block ID ` ^kioku-<ランダム10文字>` を追記するだけで原文は変えない。ポップアップで編集した場合は直後に `%%kioku-edit:kioku-<10文字> … %%` の編集記録を足す。直後に文が続くブロックには空行を1行挿入して ID を段落末に置く（ユーザー決定）。ID は内容ハッシュでなくランダム。
- **Excalidraw 本文範囲**：Excalidraw ノートは `# Excalidraw Data` 等の見出し以降と `%%` 内をすべて除外する。
- **重複**：`^kioku-` ID 付きブロックは採用済み。ID 重複は採用不可、採用済みと同内容の候補は警告のみ。
- **見送り**：M1 の「破棄」はポップアップから外すだけでノートに記録しない（再抽出で再び候補になる）。永続的な見送り記録は未決定のまま。

## M2 受入条件（LEV-276）

- 左 ribbon → 中央デッキ選択 → 問い → 回答を表示 → 評価 → 次回日程。Skip は評価なしで飛ばす操作と分ける。
- タグ適用範囲、親子デッキ、全デッキ入口、Due/New/Total、FSRS/SM-2、状態・履歴保存、Q/A 編集後の履歴は設計時に確定する（下記で確定済み）。
- 未回答の現在ノート/Vault 全体を確定要件にしない。再起動後に日程を保持し、複数デッキ所属のカードを二重出題しない。

## M2 で決めたこと（2026-10-02 利用者決定）と実装状況

詳細・理由・退けた代案は `docs/m2-design.md`、FSRS の説明は `docs/fsrs.md`、実装の構成は `docs/architecture.md`「M2」。**M2 は実装済みだが、専用 Vault での実機確認（`docs/harness.md`「M2 実機確認」）はまだで、実機で動作確認済みとは扱わない。**

- **デッキ**：設定のトリガータグ（既定 `#kioku`、複数可）を持つノートのカードがデッキに入る。子タグは子デッキ、親は子を含む。デッキ選択はノートに書かれたタグだけを平らに並べる（LEV-321、「全デッキ」の行は出さない）。タグは大文字小文字を区別せず、ノート全体に適用、frontmatter も数え、除外領域内のタグは数えない。トリガータグのないノートのカードは件数表示のみ。
- **ID 重複**：同じ `^kioku-` ID が複数ノートにあれば1枚として1回だけ出題。内容が異なれば除外して両パスを表示。カード ID は M1 と同じく大文字小文字を区別する。
- **アルゴリズム**：FSRS（ts-fsrs 5.4.2、既定パラメータ、目標保持率 90%、`enable_short_term=false`、fuzz なし）。すべての評価を履歴に保存。評価は「もう一度 / 難しい / 普通 / 簡単」（キー 1–4）。同日内の再出題なし。
- **日付と出題数**：日付の切り替えはローカル 04:00（設定可）。New は1日 20 枚（設定可、無制限も可）、上限で出ない分はデッキ選択の一覧の下（そのときだけ）と完了画面に表示し「今日だけ あと10枚 / 20枚」で増やせる。Due は上限なし。デッキ選択は「新規 / 学習中 / 復習」の3列（LEV-321、定義は `docs/m2-design.md` §13）。
- **Skip と途中終了**：Skip は `S`、何も記録せずこのセッションから外す。途中で閉じたら評価済みだけ保存、再開なし。
- **端末**：PC 1台。
- **保存**：Vault 内の見えるフォルダ `Kioku/`（名前は設定可）に Markdown 以外のファイルで、状態 JSON と年ごとの追記専用履歴 JSONL。プラグインの `data.json` は設定だけ。読めないときは書かない、保存前に `.bak`、未知の schemaVersion は読み取り専用、履歴から状態を再構築可能。ハーネスの baseline 比較に `Kioku/` を含める。
- **編集後の履歴**：Q/A を編集しても日程・履歴を保持し、内容ハッシュを記録。
- **UI**：ribbon はデッキ選択を開く。状態 modal と抽出はコマンド・file-menu・デッキ選択のボタンから。smoke を更新する。問い/答えは MarkdownRenderer で描画し、答えの表示前は埋め込みを描画しない。

## M3 受入条件（LEV-277）

- Jev は typed decision で候補を評価し、別の生成モデルで要約から Q/A を生成する。1ページから数枚、1枚1知識、原文から答えられる問いと引用。固定枚数のために根拠のない候補を作らない。
- API 未設定・失敗・タイムアウト・キャンセルと外部送信の案内。モデル認証、品質、日本語の遅延を実測してから瞬時と報告する。

## M3 で決めたこと（2026-10-02 利用者決定）と実装状況

詳細・実測計画は `docs/m3-design.md`。**M3 は部分実装（フェーズ A）・実機未確認。** ローカルの OpenAI 互換サーバーでの生成、Jev か判定なしの判定、決定的検査、同意と送信前の表示、生成カードの挿入を実装した（`docs/m3-design.md` §16）。Clef・ローカル logprobs 判定・OpenAI/カスタム生成・実測・実機確認は未実施。「瞬時」は実測（`docs/m3-design.md` §11）の前には使わない。

- **外部送信**：既定 OFF。ローカル優先（Ollama など）を案内する。外部 provider（`localhost` 経由でも外部で実行される Ollama の cloud モデルを含む）は API キーと provider ごとの同意がそろうまで使わない。
- **AI 未設定時**：決定的な検査だけ（引用の原文完全一致、答えが引用に含まれるか、重複、長さ・1枚1知識の簡易判定）。AI による Q/A 生成は AI provider を設定したときだけで、UI が理由と設定方法を説明する。
- **provider**：判定モデルを差し替えられる provider 方式の Decision Engine。Jev（TypeSafe AI）と Clef（Cloudflare Workers AI、利用者自身のアカウント）の両方を入れる。AI を有効にしたときの既定の判定 provider は Jev（キーと同意の後だけ使う）。Gemini は使わないとしていたが、2026-10-02 に改定し、有料キーの場合だけ汎用の OpenAI 互換生成の選択肢として案内する（専用 provider は作らない。`docs/m3-design.md` §2.2 G2）。Jev/Clef は文章を書けないため、要約 → Q/A には別の生成 provider（ローカルの OpenAI 互換サーバー、または同意のうえで OpenAI/カスタム）を使う。
- **範囲**：M3 はカード候補の判定と生成だけ。エージェントへのルーティングは範囲外。プラグイン内の WebGPU/ONNX 推論（Laya Multilingual を含む）は別 PoC の LEV-299。
- **確認事項への回答（2026-10-02、決定ボード第4回。すべて推奨案）**：既定の生成 provider はローカルの Ollama（推奨モデルは実測後に README で案内）。生成カードは引用元のブロックの直後に挿入（箇条書き・表・引用・callout の中なら、その全体の直後。Markdown の構造を壊さないため。同 §9 の 5）。「瞬時」の目標は日本語 2,000 字1ページで最初の候補 p50 ≤ 3 秒・全候補 p95 ≤ 10 秒。Jev は日本語の精度が目標未満でも既定のまま、実測値と注記を表示（大きく下回れば再相談）。API キーは `data.json`（`minAppVersion` 1.8.7 のまま）。Ollama の cloud モデルは同意時だけ「外部」として使える。ノート名は送らない。判定 provider が未設定なら生成を進め「未判定（Jev 未設定）」と表示。根拠が弱い候補の見せ方と1回の送信量・送信前の表示は設計判断（同 §2.1）。
- **外部の生成 API（2026-10-02 利用者決定、`docs/m3-design.md` §2.2）**：既定はローカルの Ollama のまま、外部はすべて同意と送信前の表示を通る。Groq の無料プランは、個人が自分のキー（BYOK）を Obsidian から使うことが規約上認められると確認できた場合だけ第一の推奨にし、確認までは注意付きの条件付き候補、確認できなければ推奨から外す（G1）。GPT-6 Luna（OpenAI）と Cloudflare Workers AI も候補。Gemini は有料キーの場合だけ案内し、無料枠では送信内容が製品改善に使われることと、Kioku が無料・有料のキーを区別できないことを案内に書く（G2、S4 の改定）。各社の個人 BYOK の扱いは【要確認】で、README で推奨する前に確かめる。
